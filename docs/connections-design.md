# OpenADS: self-serve account connections

Status: product direction. The first implementation slice below (Google Ads) is implemented and documented in [`docs/dev.md`](dev.md) (schema, endpoints, operator setup). Meta Ads follows the same design (self-serve Facebook Login with the operator's own Meta app, `ads_read`, long-lived tokens with expiry warnings; [`docs/SELF_HOSTING_META_ADS.md`](SELF_HOSTING_META_ADS.md)); it is implemented locally and has not been validated against a live Meta ad account. This document does not change the deployed application or its Access policy.

## First report

1. Sign in to OpenADS and open Sources. A workspace with no sources offers Connect Google Ads. Add Meta Ads as a second provider using the same screen.
2. Approve access on the provider's own screen. OpenADS login identifies the user; it does not itself authorize access to any ad account. Do not make users paste tokens, account IDs, developer tokens, or OAuth secrets.
3. Return to OpenADS. Discover the available ad accounts, including Google manager-account children. For one eligible account, select it automatically and open the report; for several, offer a named account picker with search and allow selecting more than one. Do not run an initial report for accounts the user did not select in the latter case.
4. Show the first live report. Provide explicit no-accounts, denied, and expired-access states with a single relevant action. Allow workspace admins to reconnect or disconnect a source. Do not promise one click across provider login, consent and account selection; remove avoidable clicks on our side.

## Data and security boundaries

- A workspace owns its connections and selected ad accounts. Keep `workspace`, `membership`, `connection` (provider grant) and `connected_account` (one or more selected accounts, including the Google manager context where required) distinct. Resolve membership and selected account server-side before using a connection. Admins connect; members may read allowed reports without their own provider login. Never treat an account ID supplied by a browser as authorization.
- Use a shared connection UI and lifecycle, not a universal OAuth token. Each provider implements authorization, exchange, account discovery, token lifecycle, and reporting behind the same server-side interface. Use one-time, short-lived OAuth state tied to the provider, session and workspace; PKCE where supported; exact registered callbacks. Keep provider credentials out of browser storage, responses, and logs. Encrypt per-connection grants at rest; store OAuth app secrets and encryption keys as runtime secrets, not in the database. A small D1 schema is a reasonable starting point on Workers. No global workspace ad tokens or tenant-agnostic cache keys.
- Cloudflare Access remains the outer gate for the internal beta. Product login and workspace membership must not depend on Cloudflare allowlists as the public signup mechanism. The open-source distribution can accept instance-level OAuth app settings from the operator; hosted OpenADS would configure its own applications. End users in either setup do not supply app credentials.
- Read reports only. Google Ads does not have a dedicated read-only OAuth scope: effective permissions come from the ads account role, and OpenADS must never call mutation methods. Verify production API access for the actual OAuth project before launch. Meta uses `ads_read`; confirm App Review and Advanced Access for external accounts before opening that integration to customers.

## First implementation slice

Implement one complete Google Ads loop: Sources → OAuth → account discovery → live report → reconnect/disconnect. Use the first workspace through the same flow, not an environment-variable exception. Fix the Workers HTTP transport issue in both adapters before live calls (manual redirects, reject non-success responses); done in `src/lib/providers/http.ts`, with 3xx/5xx tests. Test two workspaces to prove isolation, failed/replayed OAuth state, expired/revoked access, single vs multiple accounts, and a seven-day report against Google Ads in the account timezone. Add Meta once the Google path validates the shared design. Defer periodic sync, queues, and warehouse storage until live latency or API quotas justify them.
